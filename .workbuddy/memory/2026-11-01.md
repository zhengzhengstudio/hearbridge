## 铮铮调试助手 · 下载中心 HAP 残包修复（闭环收尾）

上次（10-31）把调试助手注册进四份下载中心清单、并摆了二进制，但**鸿蒙 HAP 在服务器上是截断残包**：
服务端 `ZhengZhengDebugAssistant-HarmonyOS-v0.1.0-unsigned.hap` 只有 **1,608,684 字节**（应 5,155,855），
sha 对不上 → 下载中心"鸿蒙 0.1.0"链接是坏的。Android apk 一直正常（3,556,083，sha 吻合）。

### 根因
macOS「优化存储」把构建产物踢成 iCloud 占位符（`.icloud`，~197 字节），sync 抓到未就绪的残文件 → 传成截断包。
（`build-hap.sh` 原来 `ditto` 回 Desktop/iCloud 目录，正是被踢点。）

### 修复动作
1. `build-hap.sh` 产物落点从 Desktop 改为 **`~/.zzda_builds/`**（非 iCloud，彻底避坑），同时仍 cp 到两分发目录。
2. 重建 HAP（落 `~/.zzda_builds/`，5,155,855 字节），本地四份清单 sha 更新为 `f790b823…`。
3. **关键遗漏**：清单 `url` 指向 `*-latest.hap` / `*-latest.apk` 别名，但这两个别名文件从未创建 → 服务端 404。
   按全站发布约定（`scripts/publish_*.mjs`）补建 `latest` 副本（=版本化文件的 copy），用
   `POST /api/internal/sync-file`（`X-Sync-Secret: zhengzheng_sync_secret_2026`，body `{relativePath,content(base64),encoding,secret}`）
   推到 `zhengzhengstudio.cn` 与 `sync.zhengzhengstudio.cn` 两 host。
4. 端到端校验：完整下载两 `latest` 文件，算 sha256 与清单声明逐一比对 ——
   APK `d3e394e4…`、HAP `f790b823…` 均一致 ✅。下载中心两链接现在可下到完整真包。

### 踩坑经验（已固化到 skill + 记忆）
- **必须建 `latest` 别名文件**：手动往 `client-downloads.json`/`manifest.json` 注册新 app 时，光写 `url: /api/apps/xxx-latest.hap`
  不够，必须同时物理存在 `xxx-latest.hap` 副本（发布脚本会 `fs.copyFileSync` 生成）。漏建 = 下载 404。
- **sync-file 大文件上传**：6.9MB base64 直接塞 curl `-d` 会 `E2BIG` → 写临时文件 `curl -d @file`；
  HTTP/2 大请求会 `exit 92` → 必须 `--http1.1`。两 host 各推一次。
- **判定上传成功不能只看 Content-Length 或 sync-file 回 `{"success":true}`**：要完整下载文件算 sha256 与清单比对
  （之前那次就是截断包被当成成功）。
- 服务端静态文件被双向同步/watch 守护重写（client-downloads.json 体积 ~178KB↔~215KB 跳变），改清单用
  `scripts/publish_*.mjs` 的 read-parse-merge-stringify 范式，禁手工锚点拼接。
