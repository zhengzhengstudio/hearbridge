## 追加（10-17 深夜 ~ 10-18）：sync 实测 + 修 sync 逻辑

### 🔴 实测发现的 sync 缺陷（已修）
`node sync_to_termux.js` 跑完后**代码与 frame-index.json 同步成功**（线上 version 已是
`20261017-tryon-fit-molsion-spec`，474/156/318、247 陌森、247 specSource 全部到位），
**但 2026 张图片一张都没传上去** —— 线上访问新增图片返回 SPA fallback 的 HTML。

根因：watch 与初始同步两处都有
`if (isProtectedGlassesImage(...) && !args.forceGlassesAssets) continue;`
——把**新增文件也一起挡掉**了。这个保护策略的原始意图是「不覆盖 Termux 端老图」，
但实现成了「眼镜站图片一律不传」。

**修复**（`sync_to_termux.js`）：
1. 新增 `remoteFileExists(relativePath)`：GET 远程文件，按 **content-type 是否 text/html**
   判定「是否真的存在」（必须排除 SPA fallback，否则误判为已存在）。带 4s 超时 + 缓存 +
   自动在 SYNC_PORTS 间探测。
2. 新增 `shouldProtectExistingGlassesImage()`：只有远程**已存在**的老图才受保护。
3. watch 路径（原 2994 行）、初始同步路径（原 1770 行）、`noOverwrite` 计算（原 3014 行）
   三处全部改为「远程不存在 = 新增文件 → 正常上传」。
4. 已备份到 `/tmp/sync_to_termux.js.bak_*`。

实测判定正确：`app-icon.png`(老) → 已存在受保护；`thumbs/molsion_*`(新) → 不存在放行。

### ⚠️ sync 操作的三个坑
1. **Termux IP 会变**：昨晚 `192.168.11.29`，今天 `192.168.124.18`（换网络）。
   第一次跑 sync 就是因此中途断连，**从日志第 3828 行起 1070 个文件全部「连接中断」失败**，
   眼镜站图片 0 成功。ICMP 被禁但 8110/8114 端口可通 —— **判断连通性要用端口不能只用 ping**。
2. **全量同步会先传几十个大安装包**（每个 70-80MB，Windows/HarmonyOS/APK），
   眼镜站目录排在最后，跑到眼镜阶段要很久。别以为卡死了。
3. **不能在已有 sync 进程时再起一个**：先 `pgrep -f sync_to_termux.js` 确认 0 进程、
   删掉 `.sync_watch.lock` 再跑，否则两个进程互相抢端口。

### 线上路径陷阱（Termux 端）
静态挂载在**站点根**，访问眼镜站资源**不带 `glasses.zhengzhengstudio.cn/` 前缀**：
- ✅ `http://<ip>:8114/frame-index.json`
- ✅ `http://<ip>:8114/assets/thumbs/xxx.webp`
- ❌ `http://<ip>:8114/glasses.zhengzhengstudio.cn/assets/...` → 命中 SPA fallback，返回 10403B 的 HTML
**这是最容易被误判成「同步成功」的地方**：HTTP 200 但内容是 HTML。
验证时必须看 `content-type` 和 `size_download`，不能只看 200。
